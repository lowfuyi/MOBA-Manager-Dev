## 5. Finding for QA: why the UI smoke check count varies

`ScreenClubSelect._choose` seeds a new game with the clock: `int(Time.get_unix_time_from_system()) % 1000000007` (`game/src/ui/screen_club_select.gd` line 29), and `ui_smoke.gd` goes through that function. So every run plays a different season. The number of checks depends on how many games the chosen club plays: an instrumented copy (a print of `played` and `full_ui`; the project is untouched) over 8 runs gave 18 games and 5 full-UI games with **210 checks** seven times, and 21 games with 7 full-UI games (a playoff run) with **238 checks** once. Every playoff game is played through the full UI (`ui_smoke.gd` line 237), about 9 to 14 checks each, plus 2 for an auto game. The Producer saw 210 to 220 and I saw 210 and 238 in 12 runs; I did not see 220, so the exact spread is a sample of the same mechanism, not a measurement of it. Consequences for QA:

1. The check count is not an invariant; do not gate on it.
2. A failure at one seed cannot be replayed, because the seed is not printed.
3. The test is a seed lottery, which is useful as a fuzz and bad as a regression gate.
Suggestions for QA Automation (not a fix request): print the seed; run once with a fixed seed (`GameState.new_game(App.world, cid, FIXED)` instead of `_choose`) and once over a short seed list; print games played so the count is explainable. The headless logic suite does not have this problem (1823 every time).
